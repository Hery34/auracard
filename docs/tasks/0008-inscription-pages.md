# 0008 — Inscription : pages, session et parcours de bout en bout

- Statut : done (16/11/2026)
- Agent : frontend (pages) ; backend (`src/proxy.ts`, cas d'usage de lecture du profil, `playwright.config.ts`) ; test-engineer (tests unitaires du cas d'usage, E2E)
- Phase : 1 (lot « inscription + appartenance », 3/3 ; dépend de 0007)
- ADR liées : 0002, 0010

## Objectif
Une personne s'inscrit, se connecte, voit un tableau de bord minimal avec son nom et son slug, se déconnecte. Un compte existant sur l'instance peut rejoindre `carnet`. Le parcours est vérifié de bout en bout sur mobile émulé.

## Périmètre de fichiers
- Autorisé (frontend) : `src/app/(auth)/**`, `src/app/(dashboard)/**`, `src/ui/primitives/**`, `src/ui/features/auth/**`, `src/app/layout.tsx` (lien de navigation minimal).
- Autorisé (backend) : `src/proxy.ts` (nécessite l'extension du hook de périmètre par Hery), `src/domain/profile/ports.ts` (ajout du port `ProfileReader`), `src/server/repositories/supabase-profile-reader.ts`, `src/server/use-cases/get-own-profile.ts`, `src/server/container.ts`, `playwright.config.ts`, `.github/workflows/ci.yml` (variables factices de build pour le job `e2e`).
- Autorisé (test-engineer) : `tests/e2e/**`, `src/server/use-cases/get-own-profile.test.ts`, `tests/builders/`.
- Interdit : tout le reste ; aucun accès Supabase depuis `src/app`/`src/ui` (les composants appellent les Server Actions de 0007 ou reçoivent des données de Server Components appelant les cas d'usage).

## Décisions de conception (validées par Hery le 15/11/2026)
1. **Routes en français** (produit francophone) : `/inscription`, `/connexion`, `/verifier-email`, `/tableau-de-bord`, `/deconnexion` (action). Les routes techniques restent celles de l'architecture (`/p/{slug}`, `/t/`, `/q/`, `/v/`).
2. **Formulaires** : composants client feuilles (`"use client"`) avec `useActionState` sur `registerAction` / `signInAction` ; champs e-mail, mot de passe, nom affiché ; erreurs mappées en messages français (`email_taken` → lien vers la connexion, `weak_password`, `slug_unavailable`, `registration_closed`, `invalid_input`). Primitives `src/ui/primitives/` : `Button`, `Input`, `Field` (label + erreur), accessibles (cibles ≥ 44 px, contraste AA).
3. **Connexion d'un compte non membre** : le formulaire de connexion demande aussi un nom affiché, utilisé seulement si le compte rejoint `carnet` (jamais dérivé de l'e-mail, audit 0006). Message `rate_limited` : « trop de tentatives, réessayez plus tard ». Mention d'information RGPD sous les formulaires (finalité, destinataire, durée, authentification hébergée sur une instance partagée).
4. **Après inscription** : session créée → redirection `/tableau-de-bord` ; `needsEmailConfirmation` → `/verifier-email` (message : consulter sa boîte). Après connexion : si le compte n'est pas encore membre (`ensure-membership`), l'appartenance et le profil sont créés avant la redirection.
5. **`src/proxy.ts`** (ex-middleware, Next 16) : rafraîchit la session (`@supabase/ssr`, `getUser()`) et redirige un visiteur non connecté de `/tableau-de-bord` vers `/connexion`. **Confort uniquement** : chaque Server Component du tableau de bord et chaque action revérifient `getUser()`. Le hook de périmètre ne couvre pas `src/proxy.ts` : Hery l'étend pour `backend` avant le lancement.
6. **Tableau de bord minimal** : Server Component, lit le profil du compte via le client serveur (RLS `profiles_select_own`), affiche nom et slug, bouton de déconnexion (Server Action). Aucune édition (phase 2).
7. **E2E** (Playwright, projets iOS/Android existants, pile Supabase locale, `pnpm build` + `pnpm start` avec `.env.local` de Hery ou variables injectées depuis `supabase status -o env` par `playwright.config.ts` si absentes ; ce dernier point relève du backend, fichier racine) : e-mail unique par exécution (`test-{timestamp}@example.test`), nettoyage des comptes en fin de test via le client admin dans un `globalTeardown` (hors périmètre frontend).


## Contrats et acquis de la fiche 0007 (à respecter)
- Actions (`@/server/actions/auth`, `'use server'`) : `registerAction(prev, formData)` (champs `email`, `password`, `displayName`), `signInAction(prev, formData)` (champs `email`, `password`, `displayName` facultatif), `signOutAction()`. Schémas partagés : `@/server/actions/auth-schemas` (`registerSchema`, `signInSchema`).
- `ActionState = { status: 'idle' } | { status: 'error'; error: ActionError; fields?: Record<string, string> } | { status: 'check_email' }` ; `ActionError` = `invalid_input | rate_limited | email_taken | weak_password | slug_unavailable | registration_closed | invalid_credentials | email_not_confirmed | display_name_required | unexpected`. Succès → `redirect('/tableau-de-bord')` levé par l'action.
- Messages français (composant `src/ui/features/auth/action-error.tsx`) : `invalid_input` → par champ (`fields` : clé = nom du champ, message traduit côté page sans écho de la valeur) ; `rate_limited` → « Trop de tentatives, réessayez dans quelques minutes. » ; `email_taken` → « Un compte existe déjà avec cette adresse. » + lien `/connexion` ; `weak_password` → « Mot de passe trop faible (8 caractères au moins). » ; `slug_unavailable` → « Impossible de générer une adresse de profil, réessayez avec un autre nom. » ; `registration_closed` → « Les inscriptions sont fermées pour le moment. » ; `invalid_credentials` → « Adresse ou mot de passe incorrect. » (générique) ; `email_not_confirmed` → « Confirmez votre adresse e-mail avant de vous connecter. » ; `display_name_required` → affiche le champ nom avec « Indiquez le nom à afficher sur votre profil. » ; `unexpected` → « Une erreur est survenue, réessayez. ».
- Conteneur (`@/server/container`, par requête) : `createContainer(): Promise<{ registerUser; signIn; auth: AuthGateway; getOwnProfile }>` (ajout `getOwnProfile`). `auth.currentUser()` (via `getUser()`) est le point d'authentification des Server Components du tableau de bord : pas de session → `redirect('/connexion')` **dans la page**, indépendamment du proxy.
- Nouveau (backend) : port `ProfileReader { getOwn(): Promise<Result<{ id: string; slug: string; displayName: string; isPublished: boolean } | null, 'unexpected'>> }` dans `src/domain/profile/ports.ts` ; repository `makeSupabaseProfileReader(server)` (client serveur, RLS `profiles_select_own`, `select id, slug, display_name, is_published`, `maybeSingle`) ; cas d'usage `makeGetOwnProfile({ auth, profiles })` → `(): Promise<Result<{ profile: … } , 'unauthenticated' | 'unexpected'>>` (`currentUser()` nul → `unauthenticated` ; profil nul pour un compte authentifié → `ok({ profile: null })`, cas « compte non membre arrivé par cookie » : la page redirige vers `/connexion`).
- `src/proxy.ts` (Next 16, runtime Node) : `createServerClient` de `@supabase/ssr` avec **les mêmes `cookieOptions`** que `server.ts` (`httpOnly: true`, `secure` en production, `sameSite: 'lax'`), `getUser()` pour rafraîchir la session, redirection `/tableau-de-bord` → `/connexion` sans utilisateur ; `matcher` limité à `/tableau-de-bord/:path*`. **Pas de redirection inverse** des pages `(auth)` vers `/tableau-de-bord` (arbitrage 16/11/2026 : un compte connecté sans profil, après `display_name_required`, bouclerait `/connexion` ↔ `/tableau-de-bord` et sa Server Action serait redirigée) : un compte connecté qui visite `/connexion` voit le formulaire. Jamais `getSession()`. Le proxy ne protège rien : chaque page revérifie.
- `playwright.config.ts` (backend) : si `NEXT_PUBLIC_SUPABASE_URL` est absente, injecter dans `webServer.env` les valeurs de `supabase status -o env` (`API_URL`, `ANON_KEY`, `SERVICE_ROLE_KEY`) et un `RATE_LIMIT_SECRET` de test (64 `0`), sinon `.env.local` fait foi ; `webServer` = `pnpm start` après `pnpm build` (comme aujourd'hui). CI job `e2e` : variables factices satisfaisant `env.ts` pour `pnpm build` (les E2E en CI exigent la pile Supabase : fiche CI ; d'ici là le job `e2e` ne lance que le build et les tests qui n'exigent pas de compte, ou est marqué `continue-on-error` pour les specs d'authentification : à trancher par backend dans la fiche, en le disant).
- E2E (test-engineer) : `tests/e2e/auth.spec.ts` ; e-mails `e2e-{run}-{n}@example.test` ; `globalTeardown` (`tests/e2e/global-teardown.ts`) qui supprime les comptes `e2e-%` par le client admin (suppression dure) avec les variables de `supabase status -o env` ; aucune lecture de `.env*`. Les limites `signup` (10/h/adresse) s'appliquent : `127.0.0.1` hors production → au plus 10 inscriptions par heure dans la suite E2E ; prévoir ≤ 6 et réutiliser les comptes entre tests quand c'est possible.
- **Arbitrages de Hery après revue/audit (16/11/2026)** : (1) Shadcn → fiche dédiée ultérieure, primitives Tailwind conservées pour 0008 ; (2) empreinte IP de limitation de débit conservée **24 h au plus** (mention RGPD complétée maintenant, purge `pg_cron` horaire = fiche préalable à la mise en production) ; (3) E2E : **toujours la pile Supabase locale** (remplace « sinon `.env.local` fait foi ») + garde-fou refusant une URL non locale dans `webServerEnv()`. Correctifs retenus : `signOut({ scope: "local" })` et effacement des cookies `sb-*` si `signOut` échoue ; mot de passe ≥ 8 à l'inscription seulement ; bornes exportées par `auth-schemas.ts` et réutilisées par les formulaires ; résumé `role="alert"` pour `invalid_input` et `display_name_required` ; lien `email_taken` ≥ 44 px ; `src/app/(dashboard)/error.tsx` en français.
- CSP complète (nonce via `proxy.ts`) : **hors périmètre** (phase 2, arbitrage hash/nonce déjà consigné) ; `frame-ancestors 'none'` reste.

## Critères d'acceptation
1. `/inscription` : formulaire accessible (labels, `autocomplete`, erreurs annoncées) ; soumission valide → `/tableau-de-bord` avec le nom affiché et le slug ; `pnpm build` : pages `(auth)` dynamiques, aucune donnée personnelle dans le HTML du tableau de bord d'un autre compte (RLS).
2. E-mail déjà inscrit → message « compte existant » avec lien vers `/connexion` ; aucune création.
3. `/connexion` : identifiants valides → `/tableau-de-bord` ; invalides → message générique (pas d'énumération) ; compte existant non membre → appartenance et profil créés, puis tableau de bord.
4. `/tableau-de-bord` sans session → redirection `/connexion` (proxy), **et** l'accès direct au rendu serveur sans session renvoie la redirection même si le proxy est contourné (test : requête avec en-tête `x-middleware-subrequest` ou appel direct sans cookies → pas de données).
5. Déconnexion → `/connexion`, cookies de session effacés, retour arrière sans données.
6. En-têtes de sécurité et `lang="fr"` conservés ; aucun `"use client"` sur une page entière ; `pnpm check` vert ; E2E verts sur iOS et Android émulés.
7. `get-own-profile` (ports simulés) : non authentifié → `unauthenticated` sans lecture ; authentifié avec profil → `ok({ profile })` ; authentifié sans profil → `ok({ profile: null })` ; lecteur en panne → `unexpected`.
8. Tableau de bord : compte authentifié mais sans profil (cookie d'un compte d'un autre projet) → redirection `/connexion` sans fuite ; `email_not_confirmed` et `display_name_required` affichés correctement à la connexion (E2E : compte créé par le client admin sans appartenance → connexion sans nom → champ nom demandé → connexion avec nom → tableau de bord).
