# 0005 — Table `profiles`, fonctions d'autorisation, vue publique

- Statut : done (15/11/2026)
- Agent : db-architect (tests pgTAP : test-engineer)

## Objectif
Un membre de `carnet` peut posséder un profil (un seul au MVP), le lire et le modifier ; personne d'autre ne voit un profil non publié ; un visiteur anonyme n'obtient, par `carnet.get_public_profile(slug)` (bâtie sur la vue interne `carnet.public_profiles`), qu'un profil publié désigné par son slug et ses colonnes publiques. Toutes les politiques passent par des fonctions d'autorisation, prêtes pour le B2B.

## Décisions de conception (validées par Hery le 15/11/2026)
1. **Table `carnet.profiles`** : `id uuid pk default gen_random_uuid()`, `owner_id uuid not null → auth.users(id) on delete cascade`, `slug text not null unique`, `display_name text not null`, `job_title text`, `company text`, `bio text`, `avatar_url text`, `banner_url text`, `theme jsonb not null default '{}'` (*ajout audit 15/11/2026 :* `profiles_theme_check` : objet jsonb, `pg_column_size` ≤ 4096 octets), `contact_email text`, `phone text`, `website_url text`, `is_published boolean not null default false`, `is_indexable boolean not null default false` (noindex par défaut, `security.md`), `created_at`, `updated_at` (trigger `carnet.set_updated_at()`, propre à `carnet`).
2. **Un profil par utilisateur au MVP** : contrainte `unique (owner_id)`, nommée pour être levée par une migration future (`architecture.md` §4.2).
3. **Slug** : `^[a-z0-9][a-z0-9-]{1,38}[a-z0-9]$` (3 à 40 caractères, minuscules, chiffres, tirets internes ; *regex corrigée le 15/11/2026 : la forme initiale acceptait un caractère seul*), unique, immuable côté base n'est **pas** imposé (le changement de slug fera l'objet d'une règle applicative en phase 2 : redirections, QR stable).
4. **Longueurs maximales en base** (`check`) : `display_name` 80, `job_title` 80, `company` 80, `bio` 500, `contact_email` 254, `phone` 32, `website_url`/`avatar_url`/`banner_url` 2048 ; `theme` borné par `profiles_theme_check` (objet, ≤ 4096 octets). Pas de validation de format (e-mail, URL) en base : Zod côté serveur en 0006+.
5. **Fonctions d'autorisation** (`stable`, `search_path = ''`, `revoke … from public` + `grant` à `authenticated` et `service_role`) :
   - `carnet.can_edit_profile(p_profile_id uuid)` et `carnet.can_read_profile_private(p_profile_id uuid)` : `security definer` (propriétaire `postgres`) pour lire `profiles.owner_id` sans récursion de politique ; vrai si `is_member()` et le profil appartient à `auth.uid()`. Au MVP les deux ont la même définition ; elles divergeront avec le B2B (ADR 0004).
   - `carnet.can_create_profile(p_owner_id uuid)` : `security invoker` ; vrai si `is_member()` et `p_owner_id = auth.uid()`. Sert au `with check` d'insertion et d'update (empêche de céder un profil).
6. **Politiques RLS sur `profiles`**, `enable` + `force`, toutes `to authenticated`, toutes en deux temps `(select carnet.is_member()) and (select carnet.can_…(col))` (*audit 15/11/2026 :* le premier terme, non corrélé, est évalué une fois par requête et court-circuite les non-membres avant tout appel `definer`) : `profiles_select_own` (`can_read_profile_private(id)`), `profiles_insert_own` (`can_create_profile(owner_id)`), `profiles_update_own` (`using can_edit_profile(id)`, `with check can_create_profile(owner_id)`), `profiles_delete_own` (`can_edit_profile(id)`). Aucune politique `anon`.
7. **Vue `carnet.public_profiles`** : vue classique (droits du propriétaire `postgres`, donc hors RLS, c'est voulu : c'est la seule porte publique), `with (security_barrier = true)`, `where is_published`, colonnes publiques uniquement : `slug`, `display_name`, `job_title`, `company`, `bio`, `avatar_url`, `banner_url`, `theme`, `contact_email`, `phone`, `website_url`, `is_indexable`. Ni `id`, ni `owner_id`, ni horodatages. **Amendement B, validé par Hery le 15/11/2026 (audit, point élevé : vue listable en masse par la clé `anon` avec coordonnées en clair)** : aucun `select` sur la vue pour `anon` ni `authenticated` (la vue reste la définition interne, propriétaire `postgres`, `security_barrier`). L'accès public est unitaire : `carnet.get_public_profile(p_slug text) returns setof carnet.public_profiles` (`security definer`, propriétaire `postgres`, `stable`, `search_path = ''`, `rows 1`, corps `select * from carnet.public_profiles where slug = p_slug`), `revoke execute … from public`, `grant execute … to anon, authenticated, service_role`. Un profil n'est atteignable qu'en connaissant son slug, comme par la puce ou le QR ; aucun annuaire énumérable. Alternatives écartées : `security_invoker = true` + politique `anon` (structure complète exposée) ; A (vue listable sans coordonnées, annuaire public de noms) ; C (risque accepté + rate limiting, contournable par pagination).
8. **Privilèges** : `authenticated` : `select, insert, update, delete` sur `profiles` (filtrés par RLS) ; `service_role` : tout ; `anon` : *(amendé B)* aucun privilège sur la vue ni sur la table ; `execute` sur `get_public_profile(text)` uniquement. Index : `slug` (unique), `owner_id` (unique). Pas de publication Realtime.

## Critères d'acceptation
1. Structure : table, colonnes, types, défauts, contraintes nommées (`profiles_pkey`, `profiles_slug_key`, `profiles_owner_id_key`, `profiles_slug_format_check`, `profiles_theme_check`, `check` de longueurs), FK cascade, trigger `updated_at` (`now()`), RLS `enable` + `force`. Aucun objet dans `public`.
2. Fonctions : propriétés (`definer`/`invoker` selon décision 5, `stable`, `search_path = ''`, propriétaire `postgres` avec `bypassrls` pour les `definer`), privilèges (`anon`/`public` sans `execute`), invariant « aucune fonction de `carnet` exécutable par `public` ».
3. Politiques : exactement les quatre nommées, `polroles = {authenticated}`, commandes `select`/`insert`/`update`/`delete`, `pg_get_expr` contenant `(select carnet.can_…` pour chacune. Invariants : « toute politique de `carnet` a un `polroles` explicite », « aucune politique `anon`/`public` ne référence `is_member` ni `can_` », « toute table de `carnet` a `relforcerowsecurity` ».
4. Personas (membre A propriétaire, membre A2 du même projet, C membre d'un autre projet, B authentifié non membre, anonyme) : A lit, crée (un seul : second insert → 23505 `profiles_owner_id_key`), modifie, supprime son profil ; A ne peut pas céder son profil (`update owner_id` → 42501 ou 0 ligne selon le chemin, à préciser par le test) ; A2 ne lit pas le profil non publié de A, ne le modifie pas, ne le supprime pas, ne peut pas insérer un profil pour A ; C et B : aucune ligne, aucune écriture ; anonyme : 42501 sur la table.
5. Vue publique et accès unitaire (amendé B) : la vue existe, `security_barrier`, colonnes de la décision 7 (`columns_are`), aucune colonne `id`/`owner_id` ; `anon`, `authenticated` et `public` n'ont **aucun** privilège sur la vue (42501 en `select` direct) ; `get_public_profile(slug)` existe (`definer`, `stable`, `search_path = ''`, propriétaire `bypassrls`, `execute` pour `anon`/`authenticated`/`service_role`, pas `public`) ; anonyme et A2 obtiennent par la fonction le profil de A **seulement** si `is_published` (une ligne, colonnes de la vue), zéro ligne pour un profil non publié ou un slug inconnu, jamais d'erreur.
6. Idempotence (double application) et rejouabilité des tests ; privilèges par défaut toujours nuls (sonde existante).
7. Vérification orchestrateur (amendé B) : clé `anon`, `Accept-Profile: carnet` : `GET /rest/v1/public_profiles` → 401 ; `GET /rest/v1/profiles` → 401 ; `GET /rest/v1/rpc/get_public_profile?p_slug=inconnu` → 200 `[]` ; OpenAPI `GET /rest/v1/` ne liste que `/` et `/rpc/get_public_profile` ; introspection GraphQL sans type `profiles`.
